on the action popup, we show the running state, token count and used context info all on the same row at the bottom of the chat history.

for the claude agent we only seem to report the context size that has been already used, after the conversation is done. can we improve this? can it already be shown while the conversation is still running

## Current state

The bottom row of the action popup is `ConversationMetaInfo` (`app/src/components/actions/conversation/conversation_meta_info.tsx`). It renders the run status label, the timer, the token summary (`ActionUsageSummaryOwner`) and, on the right, `ConversationContextUsage` (`conversation_context_usage.tsx`), a 16px ring whose percentage comes from `contextWindowUsedPercent(contextWindowUsage)` — `usedTokens / capacityTokens`, from `conversation_context_window.ts`. The ring reads `run.conversation.contextWindowUsage` for the live conversation, or the selected conversation's stored value when the user is looking at a historical one. It renders nothing while that value is absent.

The value reaches the renderer over an existing path that is already live for codex: the adapter emits an agent event `{ type: 'usage', usage, contextWindowUsage }`, `handleUsage` (`desktop/src/actions/agent/agent_streaming_event_handlers.js:33`) accumulates the turn usage onto the conversation total and re-emits it as a run event, `action_run.js:671` maps it to an update of kind `agentUsage` carrying `contextWindowUsage`, and `action_run_registry.ts:932` writes both onto its copy of the conversation, which is what the ring and the token summary read. Nothing in that path is turn-bound.

The two providers fill that path very differently:

* Codex reports context as part of its token-usage notifications. `handleTokenUsage` (`agent_streaming_adapter.js:565`) stores `codexContextWindowUsage(params)` — `tokenUsage.last.totalTokens` over `tokenUsage.modelContextWindow` — on the root thread state and emits a `usage` event on **every** notification, so the codex ring moves while the turn is still running.
* Claude never emits a `usage` event mid-turn. Its adapter only asks for context at the turn boundary: `handleResult` (`agent_claude_streaming_adapter.js:624`) builds the `turnCompleted` event and then calls `requestContextWindowUsage`, which writes one `control_request` of subtype `get_context_usage` and **withholds the `turnCompleted` event** until `handleContextUsageResponse` answers or `CLAUDE_CONTEXT_USAGE_TIMEOUT_MS` (1 second, line 12) fires. `completeContextUsageRequest` then emits `{ ...turnCompletedEvent, contextWindowUsage }`, and `handleTurnCompleted` (`agent_streaming_event_handlers.js:172-198`) stores it on `run.conversation` and emits the `usage` run event. That is the late report the card describes: for a Claude turn that runs ten minutes, the ring shows the *previous* turn's percentage the whole time (or nothing at all on the first turn) and only jumps when the turn ends.

The same lateness applies to the token count beside it. Claude's per-message usage *is* already collected while the turn runs: `handleAssistantCompletion` (`agent_claude_streaming_adapter.js:545-547`) calls `recordClaudeAssistantUsage(this.messageUsages, event)` for every completed assistant message, root and sub-agent alike, keyed `streamKey:messageId` so a repeated message cannot be counted twice. That map is only read at the end, in `handleResult`, where `claudeUsage(event, accumulatedClaudeUsage(this.messageUsages))` prefers the authoritative `result` usage and falls back to the accumulation. So the data for a live counter is already in memory and is simply never emitted.

`handleUsage` writes the conversation's `usage` but not its `contextWindowUsage`: only `handleTurnCompleted` does that. Today that is invisible, because the renderer keeps its own copy from the run event; it would become visible for a UI that attaches to a run mid-turn and reads the backend snapshot.

`ClaudeStreamingAdapter` holds exactly one pending context request, `this.pendingContextUsage` (`{ requestId, timeout, turnCompletedEvent }`), and `handleContextUsageResponse` ignores any response whose `request_id` does not match it. Request ids come from `contextUsageRequestSequence`, formatted `claude-context-usage-<n>`. Control traffic already flows in both directions mid-turn: Claude sends `can_use_tool` approval requests during a turn and the adapter answers them with `writeLine`, so writing a control frame while a turn is running is established behaviour — whether Claude *answers* `get_context_usage` promptly while it is busy is the one thing this feature cannot prove from the code.

Tests that pin the current behaviour: `desktop/src/actions/agent/agent_streaming_adapter.test.mjs` has Claude cases asserting the exact contents of the `writes` array (lines 115-127 and 137-141 both expect a single `get_context_usage` request per turn), plus `delays completion and maps only the matching context usage response without changing turn usage`, which asserts that `events` stays empty until the response arrives. `agent_streaming_event_handlers` behaviour is covered from `agent_runner_state.test.mjs` and `action_run.test.mjs`.

## implementation details

Decisions taken for this feature, per the card owner: Claude samples context once per completed **root** assistant message (no polling timer, so nothing fires during a long tool run until the model speaks again), and each sample also carries the turn's accumulated token usage, so the token count next to the ring becomes live too, matching codex. Codex is not touched.

* Split the pending-request bookkeeping in `ClaudeStreamingAdapter`. Keep `this.pendingContextUsage` as the turn-boundary request that gates `turnCompleted`, and add `this.pendingLiveContextUsage = { requestId, timeout }` for the mid-turn sample. Both request ids keep coming from the single `contextUsageRequestSequence`, so ids stay unique across both kinds. `handleContextUsageResponse` routes on the id: a match on `pendingContextUsage` keeps today's `completeContextUsageRequest` path, a match on `pendingLiveContextUsage` takes the new live path, and anything else is still ignored.
* Add `requestLiveContextWindowUsage()`, called from `handleAssistantCompletion` after `recordClaudeAssistantUsage`, and only when `streamKey === null` (root stream) — a sub agent's context is not the conversation's context, exactly as `handleTokenUsage` reports only the root thread for codex. It is a no-op when `this.pendingLiveContextUsage` is already set (single flight, so a burst of messages cannot queue requests), and a no-op when `this.turnStarted` is false. A failing `writeLine` clears the slot and reports nothing; it must not throw into the message pump, because a failed sample is cosmetic while a thrown error ends the conversation.
* Give the live request its own timeout constant, `CLAUDE_LIVE_CONTEXT_USAGE_TIMEOUT_MS = 10_000`, rather than reusing the 1 second turn-boundary value. The turn-boundary timeout is short because a whole event — `turnCompleted` — is being withheld behind it; the live request withholds nothing, so its timeout only exists to release the single-flight slot if Claude never answers. On expiry it clears `pendingLiveContextUsage` and emits nothing, leaving the ring on its last value.
* On the live response, emit `{ contextWindowUsage, type: 'usage', usage: accumulatedClaudeUsage(this.messageUsages) }`. Skip the emit entirely when `claudeContextWindowUsage(event)` returns `null` (malformed or unsuccessful response) — the ring keeps its last value rather than being cleared mid-turn, since `handleUsage` treats a `null` `contextWindowUsage` as "delete it". The usage figure is read at response time, not at request time, so it includes any message that completed while the request was in flight. `accumulatedClaudeUsage` returns `null` before any message usage exists; `sumAgentTokenUsage` skips `null` entries, so `handleUsage` still works and the emitted total is then just the conversation's committed usage.
* Clear `pendingLiveContextUsage` and its timeout in `handleResult`, next to the existing `streamStates.clear()` / `toolBlocks.clear()` reset block, so a response arriving after the turn ended cannot emit a stale sample on top of the turn-boundary value, and the slot never leaks into the next turn.
* The accumulated usage emitted mid-turn is provisional by design. `handleUsage` stores it in `run.liveTurnUsage` and emits `conversation.usage + turn usage` **without** committing it, and `handleTurnCompleted` later overwrites `liveTurnUsage` with Claude's authoritative `result` usage before committing it once. So the counter climbs during the turn and settles on the real figure at the end; no token is double-counted and nothing extra is written to the usage metrics.
* In `handleUsage` (`agent_streaming_event_handlers.js:33`), also apply the event's `contextWindowUsage` to `run.conversation` using the same three-way rule `handleTurnCompleted` already uses: a truthy value is assigned, an explicit `null` deletes the field, `undefined` leaves it alone. This keeps the backend snapshot in step with what the renderer is showing, so a popup opened mid-turn shows the ring immediately. It affects codex the same way and is the intended small unification.
* Tests. In `agent_streaming_adapter.test.mjs`, update the two Claude cases that assert the exact `writes` array, since a root assistant message now adds a `get_context_usage` request before the turn-boundary one. Add cases for: a completed root assistant message issuing a live request and its response emitting a `usage` event carrying both `contextWindowUsage` and the accumulated turn usage; a sub-agent assistant message (`parent_tool_use_id` set) issuing no request; a second root message issuing no second request while the first is unanswered; a malformed or error-subtype live response emitting nothing; and the turn-boundary behaviour still holding — `turnCompleted` withheld until its own response, and a live response arriving after `result` emitting nothing. Add a handler-level case asserting that a `usage` event with `contextWindowUsage` updates `run.conversation.contextWindowUsage`. Verify with `npm run typecheck` and the desktop agent suites.

## acceptance criteria

* During a running Claude turn, the context ring in the action popup's bottom row updates each time the main agent finishes an assistant message, rather than staying on the previous turn's value until the turn ends.
* On the very first turn of a new Claude conversation, the ring appears as soon as the first assistant message completes and its context response arrives, instead of only after the turn finishes.
* The token count beside the ring climbs during a Claude turn as assistant messages complete, and settles on Claude's authoritative `result` usage when the turn ends. The conversation's committed usage total, and the usage written to the metrics, are unchanged by the mid-turn samples — one turn still contributes its `result` usage exactly once.
* A sub agent finishing an assistant message triggers no context sample; only the main agent's messages do.
* While one live context request is unanswered, a further assistant message issues no second request. The next message after an answer, or after the 10 second live timeout, may issue one again.
* If Claude never answers a live request, or answers with an error or a malformed payload, the ring keeps its last value and the turn is unaffected — no error event, no cleared ring, no stalled conversation.
* Turn-boundary behaviour is unchanged: `turnCompleted` is still withheld until the end-of-turn `get_context_usage` answers or its 1 second timeout fires, and a live response arriving after the turn ended is discarded rather than overwriting the final value.
* Opening the action popup mid-turn shows the current context percentage, because the backend run conversation carries the live value and not only the last turn-boundary one.
* Codex conversations behave as before: their ring and token count still update live, with no change in cadence or values.
* `npm run typecheck` passes and the desktop agent test suites pass.
